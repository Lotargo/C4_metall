## Правила содержания

### Исходные планы и дополнения

Общий план, план операторских подтверждений и инженерный план переносить
в лендинг 1:1 с исходниками: все требования, дополнения, нумерацию, статусы,
формулы, примеры и ссылки. Убирать только номера документов из видимых названий.
Не добавлять собственные разделы или редакционные пояснения и не сокращать текст.
Соответствие исходных адресов страницам лендинга настраивать в коде сайта,
сохраняя исходные ссылки в Markdown.

В инженерном плане разделы 0–5 сохраняют текст плана руководства 1:1.
Дополнения D01–D13 внесены отдельно и должны оставаться видимыми как дополнения,
с исходной маркировкой, порядком и структурой. При переносе на сайт не объединять
их с исходными требованиями, не сокращать и не переписывать исходный текст без
прямого указания пользователя. Читаемость и редакция для заказчика не дают
разрешения менять происхождение или состав требований. Из публичных названий
убраны только номера документов 00/15/16; нумерация разделов и дополнений сохраняется.

### Описание реализации

1. Описывай только реализованное. Планы, названия старых агентов и наличие
   отдельного API не доказывают, что компонент включён в основной путь UI.
2. Прослеживай цепочку от запроса интерфейса до workflow, результата и записи.
   Для каждого исполнителя указывай условие запуска, вход, выход и тип исполнения:
   вызов модели либо обычный код.
3. Сохраняй буквальные имена таблиц, полей, артефактов и статусов. Различай
   SQL-метаданные, JSON-файлы, CSV-проекции и таблицу, показанную интерфейсом.
4. Не выдумывай значения чертежа или строки рабочей БД. Неизвестные значения,
   конфликты источника и ограничения алгоритма описывай явно.
5. Для существенных утверждений добавляй ссылку на конкретный фрагмент кода.
   Схемы SQL извлекай из объявлений таблиц; смысл утверждений проверяй вручную.
6. Отделяй назначение на чертеже от рассчитанной альтернативы, а предварительный
   маршрут — от инженерной приёмки и готовой сметы.
7. Проверка исходников подтверждает реализацию в снимке; она не подтверждает
   новый запуск модели или качество распознавания конкретного чертежа.
8. Держи общую картину читаемой; детали алгоритмов, таблиц и доказательств
   раскрывай по выбору пользователя. Используй название «Подготовка производства».

## Снимок и файлы лендинга

- `README.md`, `QA.md` — основание, границы проверки и соответствие требованиям.
- `.evidence/manifest.json`, `.evidence/source/` — локальный снимок с хешами;
  `.evidence/` исключён из Git и публикации.
- `src/data/architecture.mjs` — пояснения, узлы, связи, этапы и ссылки на исходники.
- `src/data/evidence.json` — извлечённые фрагменты и схемы.
- `public/architecture.json` — скачиваемая копия данных атласа.
- `src/pages/index.astro`, `src/scripts/atlas.ts`, `src/styles/global.css` — интерфейс.
- `src/pages/voksa.astro`, `src/data/voksa.mjs`, `src/data/voksa-screens.json` —
  разбор ВоксаТех по материалам `F:\projects\metall-dev-2\voksa-metall-comparison`.
  Кадры обновляй `scripts/register-voksa-screens.py`; шапку аккаунта не публикуй.

Обновляй снимок сознательно в рамках задачи актуализации архитектуры.
Не запускай захват автоматически при правке оформления или инструкций.
При обновлении используй `scripts/capture-source.mjs`; Go-дополнение
`scripts/capture-splav.mjs` берёт файлы из HEAD снимка и требует совпадения
с рабочим деревом. Не смешивай разные состояния исходного проекта молча.
Затем выполни `scripts/build-evidence.mjs`, вручную пересмотри описания
и обнови дату и границы снимка в материалах.

После изменения содержимого или интерфейса проверь `npm run verify:evidence`
и `npm run build`; изменённые взаимодействия проверь в браузере.
Рабочие чертежи, БД и секреты не включай в публикацию.
Для Sites используй существующий `project_id` из `.openai/hosting.json`.
