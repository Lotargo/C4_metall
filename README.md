# Подготовка производства — интерактивная презентация

Лендинг для инвесторов и заказчиков: понятный рассказ о процессе, реальные
скриншоты интерфейса и раскрываемые технические детали. Astro 7, статическая
сборка, локальные шрифты IBM Plex Sans, TypeScript и интерактивная схема C4.
Результат задачи находится только в `F:\projects\C4_metall`.

`/` — презентация для руководства и инвесторов без ссылок на код и IT-обозначений:
путь детали от чертежа до сметы, дорожечные схемы и роли агентов (на 22.10.2026,
отчёт — [docs/qa/2026-10-22-route.md](docs/qa/2026-10-22-route.md)). Глава
«Инструкции агентов» показывает полные тексты из `public/instructions/`; обновление —
`python scripts/capture-instructions.py`.
`/it/` — технический разбор, открываемый в новой вкладке ссылкой «Для IT».
Он содержит исходники, C4, контракты и схемы хранения.
`/voksa/` — разбор кабинета ВоксаТех: устройство, роли модели и кода, проверенная
арифметика, сравнение подходов и что стоит перенять. Открывается ссылкой
«Разбор ВоксаТех»; основание — `metall-dev-2/voksa-metall-comparison` (12–13.10.2026),
отчёт — [docs/qa/2026-10-13-voksa.md](docs/qa/2026-10-13-voksa.md).
`/plan/` — «Общий план» в формате документа с оглавлением: раздел «Входящие данные»
с шестью подразделами 0.1–0.6
(реализация, путь данных, скриншоты, что не выполнено и почему). Основание —
документы и отчёты `metall-dev-2` на 21.10.2026; кадры — `scripts/register-plan-screens.py`,
отчёт — [docs/qa/2026-10-21-plan.md](docs/qa/2026-10-21-plan.md).

`/results/` — результаты чтения трёх чертежей с отдельным маршрутом для каждого,
оглавлением, параметрами элементов и исходными фрагментами. Данные находятся в
`src/data/results/`, изображения — в `public/results/`. Основание и ограничения
TEST-разборов от 23.10.2026 описаны в [отчёте проверки](docs/qa/2026-10-23-results.md);
эти результаты не обновляют архитектурный снимок ниже.

`/implementation/` содержит документы плана реализации: меню документов и
оглавление слева, оформленный Markdown справа. Поддерживаются Mermaid и LaTeX
(KaTeX). `.md` из `documents/implementation/` подключаются автоматически при
сборке, включая вложенные каталоги; метаданные необязательны.
Порядок добавления и формат: [documents/README.md](documents/README.md).
На обычных страницах раздела подключён Tiptap: ввод по клику, оформление через
ПКМ, автосохранение и отмена/повтор 20 действий. Общие документы хранятся в
Firebase Firestore: каждый посетитель может редактировать без окна входа,
анонимная сессия создаётся автоматически. Сохранённые правки появляются у других
посетителей через подписку Firestore. Аварийные черновики остаются в браузере.
Публичная конфигурация — `src/data/firebase.json`, правила — `firestore.rules`.
При отключённой конфигурации Firebase остаётся прежний локальный dev API;
его данные в `.local/implementation/` сохранены отдельно.
Проверка Firebase: [docs/qa/2026-10-27-editor-firebase.md](docs/qa/2026-10-27-editor-firebase.md).
Проверка переноса из пробы: [docs/qa/2026-10-27-editor-main.md](docs/qa/2026-10-27-editor-main.md).

## Работа

```powershell
npm ci
npm run dev
npm run verify:evidence
npm run typecheck
npm run build
```

Разработка: порт 4325. Просмотр статической сборки: `npm run preview`, порт 4326.
Сборка находится в `dist/`.
Проверка ссылок и схем работает из чистого клона; проверка исходных байтов
дополнительно выполняется, если доступен локальный `.evidence/source/`.

Для сознательного обновления снимка и атласа:

```powershell
node scripts/capture-source.mjs
node scripts/capture-splav.mjs
node scripts/register-screenshots.mjs
node scripts/build-evidence.mjs
```

Перед новым захватом перенесите прежний `.evidence/source` и манифест в
`.evidence/archive/<дата>-<HEAD>/`, чтобы не смешивать состояния. После нового
снимка необходимо вручную сверить пояснения и диаграммы с кодом:
генератор не выводит архитектуру автоматически и не подтверждает смысл утверждений.
Не обновляйте снимок автоматически во время чужих работ.

## Публикация

Общий запуск из PowerShell в каталоге проекта:

```powershell
npm run deploy
```

Команда запускает временную сессию Codex CLI, которая фиксирует текущие
неигнорируемые правки коммитом и публикует **один и тот же коммит** в Sites и
GitHub Pages. Новые постоянные чаты не создаются. Используются текущие модель
и настройки разрешений CLI. Нужны `node`, `npm`, `git`, `gh`, `codex`, вход
через `gh auth login` и `codex login`, а также подключённый Sites в этом
аккаунте Codex CLI. Запуск разрешён из ветки `main`; доступность инструментов
Sites проверяется до отправки на GitHub.

```powershell
npm run deploy -- -Message "Update presentation"
npm run deploy -- -SkipChecks  # если evidence и typecheck уже проверены
npm run deploy -- -DryRun      # только проверка окружения, без модели и публикации
```

`scripts/deploy-both.ps1` по умолчанию поручает CLI проверить evidence и TypeScript,
заново собрать Sites с путями от `/`, отправить исходники на обе площадки и
дождаться результатов. GitHub Actions отдельно собирает вариант `/C4_metall/`.
`-SkipChecks` пропускает проверки; обязательная сборка Sites остаётся.
`-DryRun` проверяет команды, авторизацию и локальные настройки; доступность
инструментов Sites и фактическую доставку он не подтверждает.

Результат каждого запуска — `outputs/deploy-both/<запуск>/result.json`: коммит,
отдельные статусы, URL, идентификаторы версии/деплоя Sites и запуска GitHub Actions.
Если успешно обновилась только одна площадка, команда завершается с ошибкой;
перед повтором следует прочитать отчёт. Архив и идентификаторы сохраняются для
восстановления. Сырые события CLI и временные токены не выводятся и не записываются.
Одновременный второй запуск блокируется. Проверка обвязки без моделей:
`powershell -NoProfile -File scripts/test-deploy-both.ps1`.

Sites project ID сохранён в `.openai/hosting.json`; статическая директория — `dist`.
Токены публикации не сохраняются в репозитории. Исходники и пакет публикуются
штатным Sites source helper, затем сохраняется версия и развёртывается лендинг.

Второе размещение — [GitHub Pages](https://lotargo.github.io/C4_metall/).
Workflow `.github/workflows/deploy-pages.yml` собирает и публикует `dist/`
при push в `main`; доступен и ручной запуск через Actions. В настройках Pages
выбран источник GitHub Actions. Workflow получает `SITE_URL` и `BASE_PATH`
из настроек Pages; ссылки, изображения и загрузка инструкций используют этот путь.
Без этих переменных сборка работает в корне домена, как на Sites.

Для локальной сборки варианта GitHub Pages в PowerShell:

```powershell
$env:SITE_URL = 'https://lotargo.github.io'
$env:BASE_PATH = '/C4_metall'
npm run build
Remove-Item Env:SITE_URL, Env:BASE_PATH
```

Перенос на другое статическое размещение требует загрузки `dist/`, собранной
с нужными `SITE_URL` и `BASE_PATH`.

## Интерактивность

- Светлая и тёмная темы на всех страницах: фиксированная кнопка в левом нижнем
  углу, системная тема по умолчанию и сохранение ручного выбора между переходами.
- Семь глав режима показа; кнопки и клавиатура, прокручиваемые главы, выход Escape.
- Восемь этапов с понятным рассказом и отдельными параметрами реализации.
- Разбор распознавания в четырёх действиях и подробное описание режимов и ограничений.
- Семь датированных скриншотов интерфейса, переключение и просмотр в исходном размере.
- Десять раскрываемых ролей с условиями, входом, выходом и типом исполнения.
- Смысл пяти колонок геометрии, формы записи, места хранения и пояснения SQL-строк.
- C1/C2/C3/C4 на отдельной странице для IT, четыре фокуса, связи и входы/выходы;
  перечень изменений относительно предыдущего снимка.
- Масштаб, перемещение, полный экран, SVG-экспорт и ссылка на выбранный блок.
- SQL-схемы шести групп данных, вложенная структура паспорта и виды строк таблицы.
- Поиск оснований, просмотр исходника с номерами строк и SHA-256, JSON-экспорт.
- Навигация клавиатурой, семантические вкладки, модальный просмотр кода и печать.
